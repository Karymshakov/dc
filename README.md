# ТЗ 5 «Бот поддержки на кыргызском и русском»

Решение межвузовского хакатона INAI 2026. Telegram-бот определяет язык
вопроса, находит ответ в базе FAQ учебного оператора INAI Mobile и отвечает
на том же языке.

Бот: [@inai_mobile_support_bot](https://t.me/inai_mobile_support_bot)

> **Читать начинать отсюда:** [docs/GUIDE.md](docs/GUIDE.md) — где какие
> баллы, как устроен код, путь одного вопроса от буквы до ответа, питч и
> ответы на вопросы жюри.
>
> **Разбор кода простыми словами:** [docs/CODE.md](docs/CODE.md) —
> каждый модуль и что делает каждая важная функция.

## Быстрый старт

```bash
python main.py ask "Как проверить баланс?"
```

```json
{"lang": "ru", "faq_id": 1, "confidence": 1.0, "candidates": [1, 11, 9]}
```

Из кода — та же функция:

```python
from faq_bot.answer import answer

answer("Роуминг канча турат?")
# {'lang': 'ky', 'faq_id': 4, 'confidence': 0.918, 'candidates': [4, 6, 2]}
answer("А сколько стоит?", chat_id=7)   # с контекстом диалога
```

Это и есть контракт для автопроверки. Он работает **без Telegram, без сети
и без ключей API** — проверяется тестом, который блокирует соответствующие
модули на уровне импорта.

Почему бот ответил именно так — команда `/why` в боте или ключ `--why`:

```bash
python main.py ask "Balansymdy kantip korom" --why
```

Печатает улики, по которым выбран язык, лучшую тему каждого из двух
методов поиска, уверенность после калибровки и положение относительно
порога. Объяснение собирается из тех же модулей, что и ответ.

Запуск бота:

```bash
# PowerShell
$env:TELEGRAM_BOT_TOKEN = "<токен от @BotFather>"
python main.py bot
```

Вместе с ботом поднимается веб-CRM операторов: <http://localhost:8765>.
Первый вход — администратор `admin` / `admin123!` (пароль задаётся через
`CRM_ADMIN_PASSWORD`, после входа его стоит сменить). Администратор
заводит операторов в разделе «Операторы», оператор входит под своим
логином. Историю, обучение и аналитику можно открыть и без Telegram:

```bash
python main.py crm
```

## Требования

Python 3.10 и новее. **Для `answer()` сторонних зависимостей нет** — только
стандартная библиотека.

| Пакет | Для чего | Обязателен |
|---|---|---|
| `python-telegram-bot>=20` | запуск бота | только для `main.py bot` |
| `pytest` | тесты | только для разработки |
| `rapidfuzz` | ускоряет второй метод поиска | нет, есть запасной путь на `difflib` |

Настройки берутся из переменных окружения или из файла `.env`,
который в репозиторий не попадает:

| Переменная | Зачем | Обязательна |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | запуск бота | для `main.py bot` |
| `GEMINI_API_KEY` | голосовые и переформулировка | нет |
| `REPHRASE_ENABLED` | переформулировка ответа моделью | нет (выключено) |
| `LLM_ROUTER_ENABLED` | второе мнение модели, когда поиск не уверен | нет (выключено) |
| `OPERATOR_CHAT_ID` | чат операторов, куда падают обращения | нет |
| `REPHRASE_ENABLED` | переформулировка ответов моделью | нет, выключено |
| `CRM_ADMIN_PASSWORD` | пароль первого администратора `admin` | нет, `admin123!`; применяется, только пока в базе нет администратора |
| `CRM_HOST`, `CRM_PORT` | адрес CRM | нет, `127.0.0.1:8765` |
| `CRM_DB` | файл базы CRM | нет, `data/crm.sqlite3` |
| `CRM_RETENTION_DAYS` | срок хранения переписки | нет, 30 дней |

Без любой из них решение работает — отключается только соответствующая
возможность. Для `answer()` не нужна ни одна.

> **Если в системе несколько Python.** Команда `python` и команда `python3`
> могут указывать на разные установки с разным набором пакетов. Проверить,
> что бот запустится, можно так:
>
> ```bash

> ```
>
> Если команда упала — поставьте библиотеку именно для этого интерпретатора:

> Проверки `ask` и `eval` работают на любом Python 3.10+ без установки чего бы то ни было.

## Точность

Пороги зачёта: верный `faq_id` первым в 75%, в топ-3 в 90%, язык в 90%.

| Набор | Вопросов | top-1 | top-3 | Язык |
|---|---|---|---|---|
| `tune` — на нём настраивались | 25 | 100% | 100% | 100% |
| `holdout` — открыт один раз | 15 | 100% | 100% | 100% |
| Разговорный русский | 44 | 93.2% | 100% | 100% |
| Кыргызский, включая латиницу | 40 | 82.5% | 97.5% | 100% |
| Край, сочинён враждебно | 40 | 70.0% | 85.0% | 100% |
| **Все независимые вместе** | **124** | **82.3%** | **94.4%** | **100%** |

Четвёртый критерий зачёта — **диалоги с контекстом, 3 из 5**:

| Набор | Диалогов | Пройдено | Порог |
|---|---|---|---|
| `dialogs.json` (пример задания + наши) | 11 | **10 (90.9%)** | 60% |

Диалог засчитывается целиком: ошибка в любом ходе валит весь диалог.
Единственный несдавшийся — D03: на «а сколько гигабайт дают?» после
«интернет закончился, можно докупить?» бот отвечает про остаток пакетов
(тема 2), а не про докупку (тема 7). У реплики слишком сильные
собственные слова, и контекст уступает — это цена правила «наследование
темы не должно быть жадным».

Отдельно измерен отсев внецелевых вопросов на свежем наборе
`offtopic_dev.csv`: **18 из 20**. На независимом наборе цифра ниже
(19 из 25) потому, что туда намеренно положены формулировки вплотную к
каталогу — «подключите домашний интернет», «сим карта для планшета
есть?».

**Последний ряд и есть честная оценка.** Первые два не доказывают
ничего: на размеченном наборе, по которому подбирались синонимы, 100%
достижимо подгонкой. Разрыв в **17.7 пункта** между своим и чужим
набором мы измерили сами и приводим, а не прячем.

Третий набор сочинён враждебно и порог не держит — так и задумано. Он
нужен, чтобы видеть границу: однословные запросы («баланс», «apn») и
формулировки рядом с предметной областью («подключите домашний
интернет», «сим карта для планшета есть?»), где отказ обязателен, а
похожесть высока. Прятать его, чтобы средняя цифра выглядела лучше,
значило бы повторить ту же ошибку, против которой затевалось деление.

Все 124 вопроса лежат в `data/05_support/independent/`. Проверить:

```bash
python main.py eval --split tune --errors
python main.py eval --file data/05_support/independent/all.csv --errors
python main.py eval --dialogs --errors      # диалоги с контекстом
python tools/check.py          # оба набора против порогов жюри
```

### Как мы боролись с подгонкой

Размеченный `questions_dev.csv` содержит 40 вопросов, и довести на нём
точность до 100% тривиально — достаточно перенести его формулировки в
синонимы. Жюри прогонит другие 40, и такая настройка там рассыплется.

Что сделано против этого:

1. Набор разделён на `tune` (25) и `holdout` (15), настройка только по `tune`.
2. **Мы сами нашли дыру в этой защите** и говорим о ней: состав `holdout`
   вычисляется вычитанием, оба файла лежат в репозитории. Деление
   дисциплинирует, но не гарантирует.
3. Поэтому главная проверка — **наборы, сочинённые с нуля**: три набора,
   44, 40 и 40 вопросов, лежат в репозитории, ни одного совпадения с
   размеченными данными. `tests/test_independent.py` проверяет это
   сравнением строк и **уже отработал**: при составлении наборов он нашёл
   четыре формулировки, дословно повторявшие размеченные данные, и одну,
   дословно лежавшую в словаре синонимов. Все пять заменены.
4. Тест `test_ключевые_слова_не_копируют_вопросы_открытого_набора` падает,
   если синоним дословно повторяет размеченный вопрос. Он нашёл три таких
   случая у нас, они удалены; точность при этом не изменилась.
5. Тесты независимого набора проверяют **пороги жюри (75/90/90), а не
   достигнутые значения.** Тест «не хуже, чем сейчас» превратил бы набор
   в очередную цель подгонки: подкрутить словарь под эти 124 вопроса — и
   он перестанет что-либо измерять.

### Что не работает

Перечислено честно, с причинами.

| Случай | Что происходит | Почему |
|---|---|---|
| «сколько у меня на симке денег осталось» | тема 2 вместо 1 | слово «осталось» общее, а у темы 2 несколько коротких полей с ним |
| «а почём это?» | тема 3 вместо отказа | после чистки остаётся «почем», оно похоже на «почему» из темы 3 |
| «Футболдун эсеби кандай?» | тема 1 вместо отказа | «эсеп» — омоним: счёт абонента и счёт в игре. Синонимами не разделяется |
| «такси чакыр» | язык ru вместо ky | нейтральный термин плюс голый императив не дают улик ни за один язык |

Разделяющего значения порога уверенности, которое отсекало бы все
внецелевые вопросы и не теряло настоящие, на наших данных **не
существует** — измерено, не предположено. Текущее значение выбрано по
цене ошибки: потеря настоящего вопроса бьёт и по top-1, и по top-3,
протечка внецелевого — только по одному вопросу.

## Нетипичные решения

### Интерфейс: USSD-меню, карточка, светофор

Вся предметная область — это `*100#` и USSD-команды, к которым абонент
в Кыргызстане уже привык. Поэтому `/start` показывает **меню цифрами**:

```
💰 1  Баланс жана төлөм · Баланс и оплата
🌐 2  Интернет жана пакеттер · Интернет и пакеты
📦 3  Тариф жана жазылуулар · Тариф и подписки
📱 4  SIM жана номер · SIM и номер
✈️ 5  Роуминг жана чет өлкө · Роуминг и заграница
🧑‍💼 0  Тирүү оператор · Живой оператор
```

**Цифра не имеет языка.** Её нажмёт и тот, кто читает по-кыргызски, и тот,
кто по-русски. Это доступность, а не перевод интерфейса. Свободный ввод
работает всегда, меню — запасной путь.

Экрана «выберите язык» на старте **нет намеренно**: это ровно тот барьер,
который мы снимаем. Язык определяется сам, переключатель спрятан в кнопку
на случай ошибки.

Ответ приходит **на одном языке** — том, на котором спросили. ТЗ просит
именно этого: «отвечает на том же языке». USSD-код вынесен отдельным
блоком, чтобы копироваться одним касанием. Кнопка 🇰🇬/🇷🇺 перерисовывает
ту же карточку на другом языке — новых сообщений не появляется.

Двуязычен ровно один экран — `/start`, пока язык пользователя неизвестен.

Нажатие любой кнопки **редактирует текущее сообщение**, а не отправляет
новое: раздел превращается в список тем, тема — в ответ. Двадцать нажатий
добавляют в чат ноль сообщений, это закреплено тестом.

### Ответ дозревает вместе с вопросом

Абонент редко формулирует мысль одним сообщением. Живой тест на
кыргызском это показал: человек писал «салам алейкум» / «интернетим жаман
иштеп жатат» / «эмне кылсам болот» — и получал три ответа, причём первый
не по делу.

Очевидное решение — подождать пару секунд и склеить — плохое: тогда
**каждый** одиночный вопрос ждёт эту паузу, и бот выглядит зависшим.

Сделано иначе. Первая реплика получает ответ **сразу**. Если абонент
дописывает мысль, бот не шлёт новое сообщение, а **переписывает своё**,
пересчитав ответ по всему тексту. Окно скользит от последней правки:
мысль из четырёх частей по четыре секунды не разорвётся. Правка помечена
строкой «↻ учёл ваше уточнение».

### Бот не повторяет совет, который не сработал

Второе, что показал тот же тест: на реплику «гб бар экен, бирок баары бир
иштебей жатат» («гигабайты есть, но всё равно не работает») бот повторял
прежний ответ слово в слово.

Теперь отказ распознаётся тремя способами: по словам («не помогло», «уже
проверил», «баары бир»), по повтору темы в коротком окне и по возврату к
теме, которую уже отвергли. Вместо повтора абонент получает соседние темы
раздела кнопками, а со второго отказа — оператора с причиной «совет не
помог».

Уточнение отличается от отказа по времени: реплика раньше трёх секунд —
абонент не успел прочитать ответ, значит это дописка; позже — реакция на
прочитанное. Признака прочтения в Telegram Bot API нет, поэтому это
эвристика, и она описана в [docs/DECISIONS.md](docs/DECISIONS.md).

Уверенность видна абоненту светофором: 🟢 ответ сразу, 🟡 ответ плюс
похожие темы, 🔴 ответа нет, только три кнопки. Техническое число
`confidence` превращается в понятное поведение.

### Сторож фактов — основа, а не замена LLM

**Второе мнение модели (`faq_bot/router.py`).** Когда поиск не уверен и
показывает три кнопки, модель получает вопрос и названия 15 тем и
возвращает одно число — номер темы или 0. Ответ берётся из `faq.json`
дословно, тем же путём, что и по нажатию кнопки. Всё, что не является
номером существующей темы, отбрасывается, поэтому выдумать факт модель
не может: её вывод — число. В `answer()` модуль не участвует, включается
`LLM_ROUTER_ENABLED=1`. На живой проверке: «опратр можн» → оператор,
«хочу уехать в алматы на неделю, телефон будет работать?» → роуминг,
«адм», «как ты?», «прогноз погоды» → отказ.

Бонус «LLM с RAG по FAQ без выдумки фактов» устроен так: **retrieval —
наш бесплатный правиловый движок, LLM — только формулировка, и ни одного
факта от неё не принимается на слово.**

Бот цитирует `faq.json`, поэтому выдумать факт не может в принципе. Но
может совершить ошибку опаснее: выдать **настоящий** факт от чужой темы.
Код `*111#` реален и сработает — только он от доп. интернета, а не от
баланса, и абонент получит не то, за чем пришёл.

`faq_bot/consistency.py` проверяет перед отправкой **принадлежность**
факта теме:

```
ответ темы «баланс» с кодом *111# от темы «доп. интернет»
  → НЕ согласован (ussd:*111#) → отправляется дословный текст темы 1
```

Метод перенесён из нашей работы «Контроль фактической согласованности
ответов языковой модели в настраиваемой системе AXON CRM», где на двухстах
черновиках с известной правдой он дал полноту 0,950 против 0,540 у
`self_check_facts` из NeMo Guardrails, при 52 мс и без единого обращения
к модели. Здесь одна проверка занимает **0,035 мс**.

Функция `audit_knowledge()` сама находит и называет слабое место метода:
цена «100 сом» принадлежит и теме 6, и теме 7, и подмену между ними
проверка связи не поймает.

### Переформулировка моделью: четыре сторожа и выключатель

`faq_bot/rephrase.py` берёт **найденную запись базы** и переписывает её
под формулировку абонента, не имея права выйти за неё. Порядок показа
такой: ответ из базы приходит мгновенно, а формулировка модели догоняет
**правкой того же сообщения**. Ожидания нет даже при включённой модели,
а новых сообщений в чате не появляется.

Промпту не верят — проверяют результат. Четыре сторожа, от главного:

| Сторож | Что ловит |
|---|---|
| `consistency.check` | факт из ответа принадлежит другой теме (`*111#` от доп. интернета в ответе про баланс) |
| новых цифр не бывает | любая группа цифр обязана дословно быть в записи базы |
| **потерянных цифр не бывает** | цена из базы обязана остаться в ответе (D-14) |
| длина и язык | удвоение текста и съезд с кыргызского на русский |

Срабатывание любого означает одно: абонент получает дословный текст
`faq.json`. **Худший исход улучшения — отсутствие улучшения.**

Замер на настоящей модели, десять разговорных вопросов: формулировку
показали в **5 случаях из 10**, остальные пять заменены текстом базы, из
них четыре — именно из-за потерянной цены.

Включается `REPHRASE_ENABLED=1` в `.env`. **По умолчанию выключено:**
среди прошедших сторожей встречается то, чего код не ловит — ошибка
согласования («в личного кабинете»), два прогона из трёх на одной теме
при `temperature = 0`. Обоснование целиком — D-15.

### Оценка работы абонентом

Через пять минут молчания бот предлагает оценить разговор: пять кнопок с
цифрами от 1 до 5. Цифры, а не слова, по той же причине, что и в
USSD-меню — **цифра не имеет языка**, её нажмёт и тот, кто плохо читает
по-русски, и тот, кто по-кыргызски.

Почему через пять минут, а не сразу после ответа: раньше — человек ещё
читает, и просьба выглядит как подгон; позже — он уже ушёл из чата.
Повторно один и тот же чат спрашивают не чаще раза в шесть часов. Чат,
который ведёт живой оператор, не спрашивают вовсе: «помог ли я» посреди
работы человека мешает обоим.

Низкая оценка (1 или 2) не заканчивается словом «спасибо» — к нему
добавляется предложение позвать человека. Благодарность в ответ на «вы
не помогли» это тупик.

Оценка уходит в два места сразу: в `/stats`, который работает без всякой
CRM, и в сводку CRM отдельным показателем плюс системной строкой в самой
переписке — оператор, открыв диалог, видит, чем он кончился.

Сроки и частота правятся в `bot_rules.json` без кода:
`rating_after_seconds`, `rating_repeat_hours`.

Таймер сделан обычной фоновой задачей asyncio, а не `JobQueue`: та
требует APScheduler, а ставить зависимость ради одного таймера не за что.

### Нагрузка и устойчивость — измерено, не предположено

| Что | Значение |
|---|---|
| Построение индекса при старте | 44 мс, один раз |
| Задержка `answer()`, медиана | 1,0 мс |
| p95 / p99 | 1,3 мс / 1,7 мс |
| Пропускная способность одного ядра | **926 вопросов в секунду** |
| Память: 15 000 разных чатов | ровно 10 000 записей на хранилище |

Два дефекта найдены именно замером, а не рассуждением.

**`answer()` вешался на длинном входе.** Не падал — вешался, и это
хуже. На одном длинном слове без пробелов стоимость поиска по
символьным n-граммам растёт квадратично: 1 000 знаков — 6 мс, 10 000 —
437 мс, 30 000 — 3,75 с, миллион занял бы больше часа. Первый замер на
нём и завис. Вход обрезается до `config.MAX_INPUT_CHARS` **до** разбора:
10 млн знаков теперь 6,6 мс. Обрезка, а не отказ — если вопрос в длинном
входе есть, он находится.

**Состояние разговора росло без предела.** Девять словарей по `chat_id`
(язык, счётчики частоты, окно дозревания, реплика для оператора)
заполнялись на первом сообщении и не очищались никогда. Для демонстрации
незаметно, для оператора связи — утечка и дешёвая атака: писать с
множества аккаунтов, не нарушая ни одного ограничения на частоту, потому
что сам ограничитель хранится в таком же словаре. `faq_bot/bounded.py` —
потолок 10 000 чатов и вытеснение самого старого.

Проверяется в `tests/test_load.py`.

### Конфигурация отдельно от кода

Тексты, списки слов и лимиты вынесены в `faq_bot/bot_rules.json`. У каждого
ключа есть сосед `_doc` с объяснением по-русски, поэтому поведение бота
меняет человек, а не разработчик. Схема перенесена из рабочего ассистента
AXON.

### Экономия на распознавании речи

Gemini вызывается для превращения голоса в текст и — если включён
`REPHRASE_ENABLED` — для переформулировки найденного ответа под вопрос
абонента. По умолчанию переформулировка выключена (D-15). Поиск ответа
остаётся на бесплатном правиловом движке, текстовые сообщения не стоят
ничего. Записи длиннее 60 секунд не распознаются, действуют лимиты на чат,
на час и на сутки, всё отклоняемое отклоняется **до** обращения к сети.

Офлайн-распознавание кыргызского рассматривалось: открытая модель
[AkylAI-STT-small](https://huggingface.co/kyrgyz-ai/AkylAI-STT-small)
существует, но её никто не хостит, а self-hosting означает `torch` и около
двух гигабайт зависимостей. Это сломало бы главное свойство решения —
нулевой список зависимостей у `answer()`.

Из той же экосистемы взято техническое наблюдение: у кыргызских моделей
распознавания **WER 16,3% против CER 4,5%**, то есть пословная ошибка втрое
выше посимвольной. Это объясняет, почему символьные n-граммы обошли
токенный метод на 13,6 пункта, и почему выбран именно первый.

### CRM операторов: перехват, очередь, обучение

Передача оператору в Telegram закрывает бонус ТЗ, но у поддержки есть три
задачи, которые одним чатом не решаются: не потерять ждущего абонента,
не отвечать вдвоём одному и не объяснять боту одно и то же каждый день.
Для этого рядом с ботом работает веб-CRM (`faq_bot/crm/`), без внешних
зависимостей: сервер на стандартной библиотеке, история в SQLite.

**Очередь по времени ожидания.** Диалоги разбиты на «Ждут ответа», «В
работе» и «Ведёт бот». В первой группе сортировка по самой старой
неотвеченной реплике, а не по последнему сообщению: абонент, который ждёт
двадцать минут, остаётся наверху, сколько бы новых чатов ни пришло.
Таймер ожидания меняет цвет: до 5 минут зелёный, до 15 жёлтый, дальше
красный.

**Перехват.** Оператор нажимает «Перехватить» или просто отвечает, и бот
в этом чате замолкает: реплики абонента идут только в CRM. Абонент
получает «к диалогу подключился оператор». «Вернуть боту» снимает
перехват, и бот начинает с чистого листа. Время первого ответа оператора
меряется и видно в аналитике.

**Обучение на отметках.** Реплика, на которую бот не нашёл тему, попадает
в очередь «Бот не понял» с тремя подсказанными темами. Оператор отмечает
тему, и формулировка становится синонимом этой темы. Ловушки обучения
закрыты так:

| Риск | Защита |
|---|---|
| бот выучит неверный факт от оператора | учатся только формулировки; ответ всегда дословно из `faq.json` |
| ошибочная отметка испортит бота | фраза проверяется на копии базы по открытому набору; если top-1 или top-3 упали — не принимается |
| подгонка под открытый набор | вопрос из `questions_dev.csv` выучить нельзя |
| свободный ответ оператора уйдёт абонентам | он попадает в «Предложения в базу» на проверку старшему, в бота сам не попадает |
| у жюри `answer()` поведёт себя иначе | без запущенной CRM слой выученных фраз пуст, `answer()` работает ровно на `KEYWORDS` |

Выученные фразы и одобренные предложения выгружаются в JSON, чтобы
команда перенесла их в код обычным коммитом.

**Роли.** Администратор создаёт операторов, задаёт и сбрасывает им
пароли, отключает учётные записи, одобряет предложения в базу, отменяет
выученные фразы и выгружает обучение. Оператор работает с диалогами и
размечает очередь «Бот не понял». Смена пароля и отключение сразу
закрывают все сессии этого оператора. Отключить себя или последнего
администратора нельзя.

**Оптимизация.** Новые сообщения приходят длинным опросом: пока ничего не
происходит, запросов ноль, когда происходит — задержка миллисекунды.
Догружаются только новые сообщения открытого чата. Интерфейс — три файла
без сборки и внешних CDN, отдаётся сжатым и кэшируется по ETag. Проверка
отметки занимает 0,15–0,3 с.

**Безопасность.** У каждого свой логин, пароли хранятся только как
PBKDF2-SHA256 с солью. Сессия в cookie `HttpOnly;
SameSite=Strict`, POST только с заголовком `X-CRM` (защита от CSRF),
ограничение попыток входа, строгая CSP. По умолчанию CRM слушает только
`127.0.0.1`. Текст абонента выводится только как текст, разметка из него
не исполняется. Переписка старше `CRM_RETENTION_DAYS` удаляется при
запуске.

python -m pytest -q                         # тесты
python main.py ask "Balansymdy kantip korom"

## Команда и источники

Решение использует два наших предыдущих результата:

- метод контроля фактической согласованности — из работы по AXON CRM;
- схема конфигурации поведения бота — оттуда же.

Данные, тарифы и коды в `faq.json` учебные, предоставлены организаторами.
